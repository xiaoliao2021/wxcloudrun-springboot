## 登录报 2002 的排查与修复（code2Session）

现象：真实 code 调 `/v1/auth/login` 返回 2002（code2Session 调用失败）。

日志根因：`app.log` 里是
`UnknownContentTypeException: no suitable HttpMessageConverter found for response type [interface java.util.Map] and content type [text/plain]`
——**微信 jscode2session 无论成功失败都返回 HTTP 200，且 Content-Type 是 `text/plain` 而不是 `application/json`**，
原来 `restTemplate.getForObject(url, Map.class)` 直接抛异常，真实的 errcode 被吞掉，统一变成 2002。

修复（3 处）：
1. `AuthServiceImpl.code2Session`：改成 `getForObject(url, String.class)` 拿到字符串后再用 `objectMapper.readValue` 解析；解析失败/空响应才报 2002。这样 40029→2001、40013→2003 的映射才生效。
2. `RestTemplateConfig`：给 `StringHttpMessageConverter` 设默认 UTF-8（微信 text/plain 不带 charset，默认 ISO-8859-1 会把中文 errmsg 读乱码）。
3. `login` 里 `markCodeUsed` 从 code2Session 之前移到之后——网络抖动时不再白白烧掉 code，客户端可用同一个 code 重试。

验证：同一入参现在返回 `2001 code 无效或已使用`，日志打出 `errcode=40029 errmsg=invalid code`。
40029 说明 **appid+secret 这对本身份有效**（secret 错会是 40001），但 code 不属于这个 appid——要核对后端 `WX_APPID` 与前端小游戏 appid 是否同一个；另注意 code 5 分钟有效且只能用一次。

排查这类问题的方法：直接用 curl 打 `https://api.weixin.qq.com/sns/jscode2session?appid=..&secret=..&js_code=..&grant_type=authorization_code` 看原始 errcode，比看后端日志快。

## 长连接（WebSocket）实现，按 docs/api-realtime.md

依赖：`pom.xml` 加 `spring-boot-starter-websocket`。
新增：`config/WebSocketConfig`（注册 `/ws` 和 `/v1/ws`，两个都开，64KB 帧上限）、

`ws/RoomEventSubscriber`（AFTER_COMMIT 才广播）、`ws/RoomChangedEvent`、`ws/WsFrame`。
改动：`room` 表加 `revision BIGINT`（房间级版本号），`updateStatus/updateOwner/updateConfig/touch` 都带 `revision = revision + 1`（单行 UPDATE 原子递增，多实例也不会撞号）；

`WebConfig` 的登录拦截器要放行 `/v1/ws`（握手时还没有 token，token 在连接后第一帧）。

关键设计：
- 写操作仍走 HTTP，WS 只推。RoomServiceImpl 在事务内 `publishEvent(RoomChangedEvent)`，
  `RoomEventSubscriber` 用 `@TransactionalEventListener(AFTER_COMMIT)` 广播——**提交前推会读到旧状态**。
- 广播的是全量快照 + revision，不做增量（丢帧能自愈）。
- 连接对象无状态：只存 userId/connId/订阅的 roomId，房间状态每次推送现查。多实例时需要把 broadcast 换成 Redis Pub/Sub。
- 5 秒认证窗口（close 4001）、60 秒空闲超时（4002）、token 过期发 auth.expired + 10 秒宽限、互踢 close 4003（靠 20 秒扫描器发现 session 失效）。
- `WsRealtimeBroker` → `RoomService` 单向依赖（服务层只依赖 ApplicationEventPublisher），避免了循环依赖；不要用 broker 注入 service 的写法。
- WebSocketSession.sendMessage 不能并发调用，发送时按 session 加锁。
